# Third-Driver Commands C06C / C06D / F06C / F06D (Nothing X)

## Proven facts
- Declared: `SET_THIRD_DRIVER_ADVANCE_CUSTOM_EQ_MODE = 61548` (0xF06C),
  `SET_THIRD_DRIVER_ADVANCE_CUSTOM_EQ_VALUE = 61549` (0xF06D),
  `GET_THIRD_DRIVER_ADVANCE_CUSTOM_EQ_MODE = 49260` (0xC06C),
  `GET_THIRD_DRIVER_ADVANCE_CUSTOM_EQ_VALUE = 49261` (0xC06D)
  (`ProtocolConstant.java:57-58,158-159` — same values in all four extracts).
- Builders exist: `midUnitAdvanceCustomEQMode` (SET F06C `[mode]`, GET C06C),
  `midUnitAdvanceCustomEQValue(profileIndex, EQEntity)` (SET F06D =
  `EQEntity.obtainDataPacket()`, GET C06D + getPayload `[profileIndex]`)
  (`TWSDeviceExtKt.java:227-256`). "midUnit" = mid/third driver.

## Caller search (ENTIRE extracted source)
Searched for `49260|49261|61548|61549|0xF06[C-D]|0xC06[C-D]|F06C|F06D|C06C|C06D`,
`midUnitAdvanceCustomEQMode`, `midUnitAdvanceCustomEQValue` across
`re/{dirac,proto,ldac,control,case,proto2}-src`:
**zero callers** — only the constant-table declarations match.

## Conclusion
Do NOT treat F06C/F06D as proven EQ commands. They are most plausibly a
third-driver EQ slot defined in the shared protocol but unused by every product
present in these extracts (mid-unit = third driver, cf. first-driver F04F/F050).
Status: UNKNOWN. Do not build protocol implementation on them until a caller,
product, or hardware trace proves otherwise.
